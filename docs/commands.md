# omt commands

Every command accepts `--help` and prints text for people. The commands that report state, such as `omt doctor`, `omt roles`, and `omt detect`, also print JSON with `--json`. The [spec](spec.md) describes each command in detail.

`omt install`, `omt uninstall`, `omt worktree setup`, `omt doctor`, and `omt detect --write` show the change first and ask before they write, or take `--yes`. `omt init` and `omt config init` do not ask. They create missing files and keep an existing config, with two exceptions: `omt init` adds missing lines to an existing `.omt3/.gitignore`, and `omt config init --force` replaces an existing user config.

In a project install without `omt` on `PATH`, run the commands as `.omt3/bin/omt`. After a dev-dependency install, run `npx omt`. For a one-shot run, run `npx omt3`. Outside a project that has omt as a dev dependency, `npx omt` downloads a different npm package named `omt`. The [install guide](install.md#install-the-cli) lists every channel.

| Command | What it does |
| --- | --- |
| `omt install` | Installs the skills, the links, and the starter config. It shows its plan and asks before it writes. `--yes` skips the question, and `--dry-run` writes nothing. `--hooks` adds the Claude Code hook. `--project` installs into the current project and prints the worktree setup state of the current checkout. The plan shows the harnesses that omt detects (Claude Code, Codex), and a new config gets a `"harnesses"` key when one is missing. `--capabilities <file>` takes the saved output of the T3 tool `orchestrator_capabilities` for this detection. Without it, omt reads the T3 settings and `PATH`. `--with <skill>` also installs an opt-in skill. Today the only one is `omt-swarm`. The install records the choice, so a later install or update keeps it. When the bundle no longer ships a skill that an earlier install wrote, such as `omt-grill`, `omt-help`, or `omt-loop`, the install removes that skill folder and its links, and the plan shows `remove <name> (no longer shipped)`. An unedited `omt-swarm` that the install did not select goes the same way, with `(opt-in, not selected)`. It never removes a folder that omt did not install. An edited retired skill stops the install. `--force` backs it up and removes it. |
| `omt uninstall` | Removes what `omt install` added. `--project` removes the project install. |
| `omt update` | Updates the CLI with the command of the channel that installed it, then syncs the skills in user scope and in each recorded project. A skill that you edited stays, and the output names it. A managed skill that the bundle no longer ships is removed with its links, as in `omt install`. An install of the deprecated `oh-my-t3code` package moves to `oh-my-t3`: the update installs `oh-my-t3` and removes `oh-my-t3code`. It shows its plan and asks before it writes. `--yes` skips the question, and `--dry-run` writes nothing. `--check` prints the current version, the latest version, the channel, and its update command, and writes nothing. `--skills-only` syncs the skills with the CLI that runs now and uses no network. `--project` updates only the current project. It shows defaults changes and asks before accepting them. `--yes` also accepts current defaults. On a terminal, it then offers to move old `.omt/` and `oh-my-t3code` folders with `omt migrate`. See [Update omt](install.md#update-omt). |
| `omt migrate` | Moves the folders of earlier releases: each project's `.omt/` to `.omt3/`, and `~/.config/oh-my-t3code` to `~/.config/oh-my-t3`. It lists the current project (the main checkout from a worktree), each recorded project, and the user folder, and asks once. For each project, it updates the hook command, the git exclude block, the manifest, and the skills, then runs the shim and the hook. A failed check leaves the old folder as it was. A project with an open run, or whose shim runs another omt, is skipped. When both folders exist, it moves only what the new folder lacks and asks about each file that differs. `--dry-run` writes nothing. See [Move old folders](install.md#move-old-folders). |
| `omt doctor` | Checks the runtime, the config, the defaults, the harnesses, the skills, the links, the hook, `PATH`, and T3. A managed skill that the bundle no longer ships gives the warning `no longer shipped: <names> in <agents root>; run omt install`. It shows pending defaults changes and asks before accepting them. `--yes` accepts, and `--dry-run` writes nothing and skips the daily update check. `--project` checks the project install and the worktree setup of the current checkout. |
| `omt init` | Creates what is missing in `.omt3/`: the starter config, `plans/`, and `.gitignore`, which ignores `plans/` and the other live state. It adds the missing lines to an existing `.gitignore` and keeps an existing config. Then it prints the worktree setup state of the current checkout. |
| `omt config show` | Prints the merged config before omt applies the profile. `--defaults` prints the installed release's current defaults. |
| `omt config explain` | Prints the layer that sets each value: the defaults, the user config, the project config, or a profile and the file that declares it. Below a value, an `over` line names each lower layer that the value overrides. `--profile <name>` explains that profile instead of the selected one, and `--json` prints the report as JSON. See [See where each value comes from](configuration.md#see-where-each-value-comes-from). |
| `omt config edit --web` | Starts a local editor for the user config and the project config, and opens it in the default browser. `--no-open` only prints the URL. `--capabilities <file>` gives the role editor the T3 providers and models. Before each write, the page shows the diff and the config check. A write keeps the comments of the file, and it fails when it adds a config error or when the file changed on disk. The editor runs on 127.0.0.1 until you press Ctrl-C or close its tab. See [Edit the config in a browser](configuration.md#edit-the-config-in-a-browser). |
| `omt config path` | Prints the paths of the user config and the project config, and whether each exists. |
| `omt config validate` | Reports problems in both config files and in every profile. Exits 1 on an error. |
| `omt config init` | Writes the starter user config. `--force` overwrites an existing file. |
| `omt detect` | Prints which harnesses (`claudeAgent`, `codex`) can run child tasks, the `"harnesses"` value that fits, and its effect on the roles. `--capabilities <file>` uses the saved output of `orchestrator_capabilities`. `--write` sets or removes the `"harnesses"` key of one config file. It takes `--user`, `--project`, `--dry-run`, and `--yes`. See [Match the harnesses on your machine](configuration.md#match-the-harnesses-on-your-machine). |
| `omt roles` | Prints how every role resolves. |
| `omt route <role>` | Prints the `delegate_task` arguments for one role as JSON. `--against <provider\|driver\|auto>` names the worker that a cross-family role reviews. |
| `omt brief <role> --task <text>` | Renders a brief. `--save --json` saves the brief and returns a short dispatch task and its `targetKey`. With `--plan` and `--unit` too, it checks the parallel limit, records the start in the ledger, and returns the `ledger.done` command. At the limit, it writes nothing and exits 75. `--fallback` picks the next target that this unit, role, and round have not tried. With `--save` the ledger holds the tried targets, and without it you pass each one with `--tried <targetKey>` and set `--attempt`. `--strict` with `--against` exits 1 when only the worker's own family is left. |
| `omt profile` | Lists the profiles. `show [<name>] [--plan <slug>] --json` shows the resolved workflow settings. |
| `omt lock` | Runs a command under a shared build lock, or lists the held and free locks. |
| `omt git` | Applies the profile's `workflow.git` policy to git actions. `check <commit\|push\|pr\|merge>` prints `auto`, `ask`, or `off` with the reason, and writes nothing. `behind [--ff]` counts the commits of the default branch that `HEAD` lacks, with no fetch, and with `--ff` fast-forwards a clean tree. `start (--plan <slug>\|--run <id>)` records the paths that were already changed before a run. `commit -m <message>` commits only the paths that the run changed since `start`; `--path` limits it to some of them. `pr --title <text> --body-file <file>` pushes the branch and opens a draft PR, or a ready one with `--ready`, or prints `split:` when the PR would change more than `maxPrFiles` files. `pr --pr <number>` pushes to that PR only and never opens one; it asks when the PR comes from a fork, is on another branch, or is by another author. `stack <sha>,<sha>...` pushes every slice branch in one atomic push and opens one PR per slice, each based on the slice below. `commit`, `pr`, and `stack` take one of `--plan` and `--run`, and print `ask:` or `off:` instead of acting when the policy says so. `--yes` means that you approved the action in this run. They run `gh`, and `pr` and `stack` push to `origin`. See [Commit, push, and open a PR](workflows.md#commit-push-and-open-a-pr). |
| `omt plan` | Creates plan files and shows their progress. `new --profile <name>` selects a profile, and `new <slug> --light` leaves out the oracle item. `profile <slug> <name\|none>` switches the profile. `mark <slug> <id> <done\|open\|blocked>` marks one item. `limit <slug> <n\|none>` sets or removes the plan's parallel limit. A run has no task budget, so `--tasks` and `--max-tasks` fail with a usage error. `status <slug>` prints the next item, the `ready:` units, and a `warning:` line for each dependency that names no unit or names its own unit. It prints one warning for the first dependency cycle only, and one for a `max-tasks` header key, which has no effect. |
| `omt ledger` | Records and counts the delegated tasks in `.omt3/ledger.jsonl`. `omt brief --save --json` records each start. `done <requestId>` closes it with `--verdict`, `--status`, `--task-id`, and `--note`, and prints `closed ...` and a `settle:` line: `settle: allowed`, or `settle: no (linked worktree)`. `settle-check` prints only the `settle:` line and writes nothing. `add` appends an entry by hand, for the track threads of `omt-swarm`. A terminal entry closes the start with the same `clientRequestId`, else the same task id, else the same plan, unit, role, round, and attempt. `stats` prints `can dispatch: yes` while fewer than `maxParallel` tasks are active. The number of tasks that a run started never stops a dispatch. |
| `omt worktree` | `check` (the default) reports the current checkout's package manager, lockfile, linker settings, `t3.json` setup script, and the T3 activation step. It writes nothing and starts no process. `setup [--dry-run] [--yes]` writes a missing `t3.json` and `.t3/omt-worktree-setup.mjs` for a Bun or pnpm project, and for pnpm a missing `pnpm-workspace.yaml` with `enableGlobalVirtualStore: true`. The runner installs dependencies into a global virtual store before the agent starts. Neither subcommand rewrites an existing file. In a linked worktree, the files go into that worktree. |
| `omt paths` | Prints the absolute paths of the project root, `.omt3`, the plans, the grills, the ledger, the evidence directory, the project config, and the shim. In a linked git worktree, the paths point into the main checkout. `--json` prints them as an object. `--grills` prints only the grills directory, which holds the files of the retired `omt-grill` skill. |
| `omt help [<command>]` | Prints the command list, or the help of one command. It prints the same text as `omt --help` and `omt <command> --help`. |
| `omt hook user-prompt-submit` | Runs the Claude Code hook. The hook calls this command. You do not run it. |

`omt route` and `omt brief --json` take `--against <provider|driver|auto>` for a cross-family role. A provider id or a driver kind names the worker whose change the role reviews. `auto` reads that worker from `.omt3/ledger.jsonl` and needs `--plan <slug>`.
