# omt commands

Every command accepts `--help` and prints text for people. The commands that report state, such as `omt doctor`, `omt roles`, and `omt detect`, also print JSON with `--json`. The [spec](spec.md) describes each command in detail.

`omt install`, `omt uninstall`, `omt worktree setup`, `omt doctor`, and `omt detect --write` show the change first and ask before they write, or take `--yes`. `omt init` and `omt config init` do not ask. They create missing files and keep an existing config, with two exceptions: `omt init` adds missing lines to an existing `.omt3/.gitignore`, and `omt config init --force` replaces an existing user config.

In a project install without `omt` on `PATH`, run the commands as `.omt3/bin/omt`. After a dev-dependency install, run `npx omt`. For a one-shot run, run `npx omt3`. Outside a project that has omt as a dev dependency, `npx omt` downloads a different npm package named `omt`. The [install guide](install.md#install-the-cli) lists every channel.

| Command | What it does |
| --- | --- |
| `omt install` | Installs the skills, the links, and the starter config. It shows its plan and asks before it writes. `--yes` skips the question, and `--dry-run` writes nothing. `--project` installs into the current project and prints the worktree setup state of the current checkout. The plan shows the harnesses that omt detects (Claude Code, Codex), and a new config gets a `"harnesses"` key when one is missing. `--capabilities <file>` takes the saved output of the T3 tool `orchestrator_capabilities` for this detection. Without it, omt reads the T3 settings and `PATH`. When the bundle no longer ships a skill that an earlier install wrote, such as `omt-research` or `omt-swarm`, the install removes that skill folder and its links, and the plan shows `remove <name> (no longer shipped)`. It never removes a folder that omt did not install. An edited retired skill stops the install. `--force` backs it up and removes it. The install also removes what other retired features left: the Claude prompt hook of an earlier `--hooks` install, from the settings file that it was written to (it drops only that entry and backs the file up first), the retired config keys, such as `limits.maxParallel`, and in a project `.omt3/ledger.jsonl` and `.omt3/locks/`. A user install also copies the omt T3 workflow file `omt.ts` into `T3CODE_WORKFLOWS` or `~/.t3/workflows`, when the T3 home exists. It keeps the old file while a run of its workflows is unfinished. |
| `omt uninstall` | Removes what `omt install` added, also the T3 workflow file, unless a run of its workflows is unfinished. `--project` removes the project install. |
| `omt update` | Updates the CLI with the command of the channel that installed it, then syncs the skills in user scope and in each recorded project. A skill that you edited stays, and the output names it. A managed skill that the bundle no longer ships is removed with its links, and the other retired features are cleaned up, as in `omt install`. An install of the deprecated `oh-my-t3code` package moves to `oh-my-t3`: the update installs `oh-my-t3` and removes `oh-my-t3code`. It shows its plan and asks before it writes. `--yes` skips the question, and `--dry-run` writes nothing. `--check` prints the current version, the latest version, the channel, and its update command, and writes nothing. `--skills-only` syncs the skills with the CLI that runs now and uses no network. `--project` updates only the current project. It shows defaults changes and asks `Use the current defaults? [Y/n]`, where Enter accepts. Scopes with the same changes share one diff and one question. `--yes` also accepts current defaults. See [Update omt](install.md#update-omt). |
| `omt doctor` | Checks the runtime, the config, the defaults, the harnesses, the skills, the links, `PATH`, T3, and the T3 workflow file, with whether T3 Workflows is on, which `omt-climb` needs. A managed skill that the bundle no longer ships gives the warning `no longer shipped: <names> in <agents root>; run omt install`. A `hooks` warning shows only while the retired Claude prompt hook is still in a settings file; `omt update` removes it. It shows pending defaults changes and asks `Use the current defaults? [Y/n]`, where Enter accepts. `--yes` accepts, and `--dry-run` writes nothing and skips the daily update check. `--project` checks the project install and the worktree setup of the current checkout. |
| `omt init` | Creates what is missing in `.omt3/`: the starter config, `plans/`, and `.gitignore`, which ignores `plans/` and the other live state. It adds the missing lines to an existing `.gitignore` and keeps an existing config. Then it prints the worktree setup state of the current checkout. |
| `omt config show` | Prints the merged config before omt applies the profile. `--defaults` prints the installed release's current defaults. |
| `omt config explain` | Prints the layer that sets each value: the defaults, the user config, the project config, or a profile and the file that declares it. Below a value, an `over` line names each lower layer that the value overrides. `--profile <name>` explains that profile instead of the selected one, and `--json` prints the report as JSON. See [See where each value comes from](configuration.md#see-where-each-value-comes-from). |
| `omt config path` | Prints the paths of the user config and the project config, and whether each exists. |
| `omt config validate` | Reports problems in both config files and in every profile. Exits 1 on an error. |
| `omt config init` | Writes the starter user config. `--force` overwrites an existing file. |
| `omt detect` | Prints which harnesses (`claudeAgent`, `codex`) can run child tasks, the `"harnesses"` value that fits, and its effect on the roles. `--capabilities <file>` uses the saved output of `orchestrator_capabilities`. `--write` sets or removes the `"harnesses"` key of one config file. It takes `--user`, `--project`, `--dry-run`, and `--yes`. See [Match the harnesses on your machine](configuration.md#match-the-harnesses-on-your-machine). |
| `omt roles` | Prints how every role resolves. |
| `omt route <role>` | Prints the `delegate_task` arguments for one role as JSON. `--against <provider\|driver>` names the worker that a cross-family role reviews. |
| `omt brief <role> --task <text>` | Renders a brief. `--save --json` saves the brief and returns a short dispatch task and its `targetKey`. `--fallback --attempt <n>` picks the next target that is not in `--tried`: pass one `--tried <targetKey>` for each target that failed. omt keeps no record of the attempts. `--strict` with `--against` exits 1 when only the worker's own family is left, and leaves that family out of the fallbacks. `--workflow` writes the brief for a T3 workflow agent: it commits in its own worktree and returns structured output. |
| `omt profile` | Lists the profiles. `show [<name>] [--plan <slug>] --json` shows the resolved workflow settings. |
| `omt git` | `start (--plan <slug>\|--run <id>)` records the paths that were already changed before a run. `commit -m <message>` with the same id commits only the paths that the run changed since `start`; `--path` limits it to some of them. It prints `ask:` and commits nothing when a path had changes before the run and changed again; `--include <path>` takes that path too. See [Commit, push, and open a PR](workflows.md#commit-push-and-open-a-pr). |
| `omt plan` | Creates plan files and shows their progress. `new --profile <name>` selects a profile, and `new <slug> --light` leaves out the oracle item. `profile <slug> <name\|none>` switches the profile. `mark <slug> <id> <done\|open\|blocked>` marks one item. A run has no task budget, so `--tasks` and `--max-tasks` fail with a usage error. `status <slug>` prints the next item, the `ready:` units, and a `warning:` line for each dependency that names no unit or names its own unit. It prints one warning for the first dependency cycle only, and one for each `max-tasks` or `max-parallel` header key, which has no effect. |
| `omt worktree` | `check` (the default) reports the current checkout's package manager, lockfile, linker settings, `t3.json` setup script, and the T3 activation step. It writes nothing and starts no process. `setup [--dry-run] [--yes]` writes a missing `t3.json` and `.t3/omt-worktree-setup.mjs` for a Bun or pnpm project, and for pnpm a missing `pnpm-workspace.yaml` with `enableGlobalVirtualStore: true`. The runner installs dependencies into a global virtual store before the agent starts. Neither subcommand rewrites an existing file. In a linked worktree, the files go into that worktree. |
| `omt paths` | Prints the absolute paths of the project root, `.omt3`, the plans, the grills, the evidence directory, the project config, and the shim. In a linked git worktree, the paths point into the main checkout. `--json` prints them as an object. `--grills` prints only the grills directory, which holds the files of the retired `omt-grill` skill. |
| `omt help [<command>]` | Prints the command list, or the help of one command. It prints the same text as `omt --help` and `omt <command> --help`. |

`omt route` and `omt brief --json` take `--against <provider|driver>` for a cross-family role. A provider id or a driver kind names the worker whose change the role reviews.

`omt hook`, `omt ledger`, `omt lock`, and `omt migrate` were removed: T3 now tracks child tasks, parallel work runs in worktrees, and `$omt-ulw` works on every provider. omt still reads a `.omt/` or `oh-my-t3code` folder of an earlier release.
